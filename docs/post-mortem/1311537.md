# AB#1311537

## Executive Summary

Teams building on `auro-popover` could restyle the popover's outer bubble but nothing inside it — most importantly the small pointer (the "arrow") that connects the bubble to whatever triggers it. That left teams with two bad options: ship a popover that didn't match their layout, or build a workaround. It also generated one-off styling requests to the design system team.

This change opens up the arrow and the trigger wrapper for external styling, and documents them — along with the outer bubble, which had been styleable since 2023 but was never written down anywhere. Teams can now adjust the arrow's appearance and correct how a popover lines up with its trigger using their own CSS.

The change is additive. Nothing about the popover's default appearance changes, and existing consumers are unaffected.

Ticket: [AB#1311537](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1311537)

## The Problem

A web component can seal its internal structure off from the outside world, which is normally a feature — it stops a team's stylesheet from accidentally breaking the component. But it also means the component has to deliberately open specific pieces up for styling, one at a time.

`auro-popover` had only ever opened up one piece: the outer bubble. The arrow and the wrapper around the trigger stayed sealed. So a team whose tooltip didn't line up with the icon it described had no way to correct it, no matter what CSS they wrote — the styles simply had no effect. This was originally reported in GitHub issue [AlaskaAirlines/auro-popover#93](https://github.com/AlaskaAirlines/auro-popover/issues/93), which was closed as *not planned* before this ticket revived it.

There was a second, quieter problem. Even the one piece that *was* open for styling had never been documented — it appeared in no API reference and no machine-readable component manifest. A consumer had no way to discover it short of reading the component's source.

## Root Cause

Two separate causes, one structural and one documentation-level.

**1. Missing `part` attributes.** In `src/auro-popover.js`'s `render()`, only the bubble carried a part attribute:

```html
<div id="popover" class="popover util_insetLg body-default" popover="manual" part="popover" ...>
  <div id="arrow" class="arrow" data-popper-arrow></div>   <!-- no part -->
  <slot></slot>
</div>
<span role="presentation">                                  <!-- no part -->
  <slot name="trigger" data-trigger-placement="${this.placement}"></slot>
</span>
```

Without a `part` attribute, an element is unreachable by an outer `::part()` selector — shadow DOM encapsulation blocks everything else. `part="popover"` was added in December 2023 (commit `a6e49d2`); the arrow and trigger wrapper were simply never given the same treatment.

**2. Missing `@csspart` JSDoc tags.** The `part` attribute makes an element *styleable*; it does nothing to make it *discoverable*. In this toolchain, discoverability comes from a `@csspart <name> - <description>` tag in the class JSDoc, which the analyzer lifts into `cssParts` in `custom-elements.json`, from which the build generates a `### CSS Shadow Parts` table in the API docs. The class JSDoc declared `@customElement` and two `@slot` tags but no `@csspart`, so `custom-elements.json` had no `cssParts` key at all and the docs had no parts table — which is why `part="popover"` went undocumented for nearly two years.

**A complication worth naming.** The visible arrow is not the `.arrow` element. That div is a zero-size positioning anchor; the diamond a user sees is its `::before` pseudo-element — a 12px square with a background, rotated 45° (`src/styles/style.scss:156-167`, `src/styles/color.scss:21-26`). Exposing `part="arrow"` without saying this would have handed consumers a part that appears to do nothing.

## The Fix

**Expose the two elements** (`src/auro-popover.js`, `render()`):

```html
<div id="arrow" class="arrow" data-popper-arrow part="arrow"></div>
<span role="presentation" part="trigger">
```

**Document all three parts** via `@csspart` tags on the class, including backfilling the previously-undocumented `popover`. This populates `cssParts` in `custom-elements.json` and auto-generates the `### CSS Shadow Parts` table in `docs/api.md` and `demo/api.md`. The `arrow` description carries the two non-obvious constraints — target `::part(arrow)::before` for the visible shape, and position is not overridable.

**Add consumer-facing documentation** — a new "Style Component with CSS Shadow Parts" section in `docs/partials/api.md` (the hand-authored source; `docs/api.md` and `README.md` are generated), plus a live example at `apiExamples/cssParts.html` demonstrating all three parts, including the `auro-icon` trigger case from the original issue.

**Add regression tests** — two new blocks in `test/auro-popover.test.js`:

- `"auro-popover — CSS shadow parts"` — the part name on each of the three elements, the `data-popper-arrow` hook, preservation across a show/hide cycle, and a computed-style test proving an outer `::part(arrow)::before` rule takes effect.
- `"auro-popover — default appearance"` — the arrow's default background matches the bubble (asserted as an invariant, since drift between them shows as a seam), its 12px dimensions, and its rotation per resolved placement. These stand in for screenshot-based visual regression, which this repo has no harness for.

Those two blocks took the suite from 69 to 79 tests; later review follow-ups brought it to 83.

**Separately**, two dead declarations were removed from the arrow's styles — see "Dead Declarations Removed" below. Landed as its own commit so the styling contract and the cleanup stay independently reviewable.

Every commit on this branch is tagged `AB#1311537`. The styling contract itself landed as a formatting-only pass (`style:`), the shadow parts (`feat:`), and the dead-declaration cleanup (`fix:`). Work unrelated to the parts change was already on the branch — issue-template edits, the attribute-casing fix, and the dependency bump — and the last two of those change shipped output, so they are accounted for below rather than left for a reviewer to discover. The rest apply code-review follow-ups: this accounting, a stale line in `docs/why-popover.md`, a contrast fix in the parts example, a caveat that the `trigger` part is inert under `for`, coverage for the `addspace`/`removespace` attribute mapping, and a test-timing guard.

- **`chore: remove project references from issue templates`** — edits seven `.github/ISSUE_TEMPLATE/*.yaml` files. No effect on shipped code.
- **`fix: standardize attribute casing to address CEM warnings`** — declares `attribute: "addspace"` / `attribute: "removespace"` explicitly on the two reactive properties, and renames the matching selectors in `style.scss` plus the documented names across `docs/`, `demo/`, and `apiExamples/`. This is a no-op at runtime and not a breaking change: Lit's `__attributeNameForProperty` already lowercases property names by default, so `addspace`/`removespace` were the observed and reflected attribute names *before* this change — the explicit option only silences the CEM analyzer. Property names are unchanged, so framework property bindings are unaffected; and attribute names in CSS selectors match ASCII case-insensitively for HTML elements in HTML documents, so `[removeSpace]` already matched `removespace`.
- **`chore: update dependencies`** — see below.

### The dependency bump, and why it needed checking

The bump moves `webcorestylesheets` `^11.1.3 → ^12.0.1` (major), `design-tokens` `^9.1.0 → ^9.3.3` (minor), `auro-library` `^5.13.1 → ^5.14.1`, and `lit` `^3.3.2 → ^3.3.3`.

The major bump deserved scrutiny rather than a rubber stamp, because `webcorestylesheets` is a devDependency in name only: `style.scss` `@use`s its type classes, `core`, `breakpoints`, and `insetUtility`, all of which compile into the component's shipped CSS at build time. That makes it the single change on this branch most capable of falsifying the claim this document repeats elsewhere — that default appearance is unchanged.

What v12 actually changed, per the lockfile: webcore's own `design-tokens` requirement went `^8.19.0 → ^9.3.3`, which removed the nested `design-tokens@8.21.2` copy webcore had been carrying and deduped it to the single hoisted `9.3.3`. So webcore's SCSS now resolves tokens against 9.3.3 instead of its own private 8.21.2. The component's *own* styles were already on the hoisted copy and moved only a minor version.

What was checked after the bump, stated precisely, because the obvious claim here is wrong. `npm run build` compiles without errors and the full suite passes 79/79 with v12 installed. It is tempting to read the `"default appearance"` block added by this ticket as verification that appearance survived the bump — it is not. That block pins the arrow's background against the bubble's, its 12px dimensions, and its per-placement rotation, and all three resolve from design tokens and static SCSS, not from anything `webcorestylesheets` contributes: the background assertion compares two declarations that read the *same* custom property, the 12px comes from `--ds-size-150`, and the rotations are hardcoded `rotate()` values.

What v12 actually feeds into the bundle is the bubble's padding (`util_insetLg`), the type classes, and the responsive `max-width` — and the suite asserts none of those. So the passing build and suite show the bump did not break compilation or the arrow's styling contract. They are *not* evidence that webcore-driven padding, type, or breakpoint rendering is unchanged. Closing that gap needs computed-style assertions on the popover's padding, font-size, and max-width; it is filed as a follow-up rather than done here, and until then the honest statement about this bump is "not verified," not "verified."

One real change v12 does introduce: it emits a new deprecation warning for the inset utility that `style.scss` still `@use`s — `Deprecated: Inset utility selectors and mixin`. The build succeeds and the utility still works, so this is not blocking, but migrating off it is a follow-up.

## Why This Works

**The cascade favors the consumer.** For `::part()`, a normal declaration in the outer page beats declarations inside the shadow tree regardless of specificity. The only `!important` in the component's stylesheet is on `.popover { margin }` for the `addspace`/`removespace` attributes — none of the arrow rules use it — so consumer overrides win. Six selector forms were tested in real Chrome (unscoped, class-scoped, id-scoped, `!important`, the part element itself, and a property the shadow tree never sets); all six applied.

**`::part(arrow)::before` is valid.** The Shadow Parts spec permits a pseudo-element selector after `::part()`, which is what makes the visible diamond reachable. What is *not* reachable is anything inside a part — hence exposing the anchor element rather than trying to expose the pseudo-element directly.

**The part attribute is inert to Popper.** Popper resolves the arrow via `[data-popper-arrow]`, which is untouched, so positioning behavior is unchanged. A test pins that attribute so a future refactor can't quietly break positioning while leaving the part in place.

**The positional boundary is real, and was confirmed rather than assumed.** Popper's default `arrow` modifier is active — the component passes a partial `modifiers` array, which Popper merges with its defaults rather than replacing them. Inspecting a live popover shows the arrow carrying inline `position: absolute` and `transform: translate(97px, 0px)`, rewritten on every show. Inline styles beat `::part()` rules, so positional overrides on `::part(arrow)` cannot work and were not promised. The `rotate()` transform lives on `::before`, which Popper never touches, so appearance overrides are safe. The docs state this boundary explicitly rather than letting consumers discover it by failure.

**Naming was chosen, not defaulted.** Unprefixed `arrow` and `trigger` match the already-shipped `part="popover"` and `auro-accordion`'s `trigger`/`content`/`chevron`, rather than the newer prefixed style in `auro-alert` (`alert-content`) or `auro-dialog` (`dialog-header`). The ticket flagged that new parts become public API that consumers will depend on, so consistency with the part this component already ships mattered more than consistency with newer siblings.

## Outcome

Teams can now style the popover's arrow and correct trigger alignment with their own CSS, without workarounds or a request to the design system team. The available styling hooks are listed in the component's API documentation with a working example, so they're discoverable rather than tribal knowledge — including the outer bubble, which was styleable but undocumented for nearly two years.

The popover looks and behaves exactly as before for anyone who doesn't opt in. There is no breaking change and no migration.

The change was checked in a real browser, not just in unit tests: the arrow recolors correctly, the trigger alignment override applies, and the default popover still renders correctly both above and below its trigger. That check caught a genuine defect in the documentation example, described below, which unit tests had passed straight over.

One limit is worth setting expectations on: the arrow's *position* remains owned by the component. Teams can change how the arrow looks, but not where it sits; the `placement` attribute chooses which side the popover appears on. This is a deliberate boundary, not an oversight — the positioning library recalculates the arrow's position on every open and would overwrite anything a consumer wrote.

## Ticket Completeness

All 5 acceptance criteria resolved. One item from the ticket's separate testing guidance was met by substitution rather than literally, and one of the ticket's open risk questions is now answered.

**Resolved**

- **Inner elements, at minimum the arrow, exposed as styleable shadow parts** — the arrow and the trigger wrapper are both exposed.
- **A consumer can apply external CSS to those parts and see the change reflected** — confirmed in real Chrome against the running dev server, not just asserted in unit tests. The arrow recolors, the bubble restyles, and the trigger alignment override applies. Note the criterion's parenthetical mentions "or reposition the arrow": repositioning is not achievable and cannot be, because the positioning library rewrites the arrow's position on every open. Appearance is adjustable; position is not. This is documented rather than left to be discovered, and was accepted as the intended scope.
- **Existing bubble styling continues to work, no regression** — the bubble's styling hook was left exactly as it was, and a test now pins it so it can't be dropped by accident.

- **New unit tests verify the exposed parts render** — ten new tests across two blocks, including one that confirms external styling genuinely reaches the arrow rather than merely checking the hook exists. A later review pass added four more covering the `addspace`/`removespace` attribute mapping. Suite grew from 69 to 83 tests, all passing.

**Met by substitution**

- **Visual regression coverage** (from the ticket's Testing notes, not the acceptance checklist) — this repo has no screenshot harness, and the Auro pattern for one (Chromatic via Storybook, as used in auro-formkit) is infrastructure this standalone component repo doesn't have; adding it is disproportionate to an "Effort - Low" ticket. Instead, a `"default appearance"` test block pins the arrow's default paint properties — background matched to the bubble, 12px dimensions, correct rotation per resolved placement — so a change to default rendering fails a test rather than shipping silently. ## Learnings

- **A `part` attribute makes an element styleable; a `@csspart` tag makes it discoverable. They are separate steps and it is easy to do only the first.** `part="popover"` shipped in December 2023 and went undocumented for nearly two years because the JSDoc tag was never added — no manifest entry, no docs table, no way to find it but reading the source. When adding a part, adding the tag is not optional polish.
- **A passing unit test does not mean the shipped example works.** The unit test injected its own CSS and passed; the actual documentation example was silently broken in the browser. Anything that only exists in generated output needs to be checked in the thing that generates it.
- **Markdown will quietly corrupt a `<style>` block injected into it.** The docs generator indents included examples by two spaces. A blank line ends the raw-HTML block, and any following line at four or more spaces becomes an indented code block — which injected `<pre><code>` *inside* the `<style>` element. CSS error recovery then discarded the rule that followed. Two of three rules survived, so the page looked fine at a glance. Keep injected `<style>` content at column zero with no blank lines.
- **CSS error recovery fails silently and asymmetrically.** The invalid token sequence consumed exactly one following rule and then resumed parsing normally, so the first and third rules worked while the second vanished. Debugging this by reading the page was misleading; enumerating `document.styleSheets` and comparing against the source was what actually found it.
- **If a part's visible rendering lives in a pseudo-element, say so loudly.** `::part(arrow)` selects an invisible anchor. A consumer who tries it, sees nothing happen, and files "the part doesn't work" is behaving reasonably.
- **When a positioning library writes inline styles to an element, exposing it as a part creates a partial contract.** Paint properties are overridable; positional ones are not, because inline styles win. Document which half a consumer gets — an undocumented partial contract reads as a bug.
- **Assert the behavior, not the attribute** — and prefer invariants to literals. An attribute-presence test passes even if the styling contract is unreachable. Asserting that the arrow's background *equals the bubble's* is more durable than asserting a hex value, and it encodes why the value matters: drift between them shows as a visible seam.
- **Derive expectations from resolved state, not requested state.** A test asserting the arrow's rotation for `placement="top"` failed, because Popper's flip modifier had moved the bubble to `bottom` — the fixture sat near the viewport edge. Reading `data-popper-placement` and mapping from that made the test correct and position-independent.
- **Auto-fixing pre-commit hooks will quietly fold unrelated formatting into a feature commit.** `lint-staged` runs `biome check --fix` here, so staging two files that already violated the config would have added ~157 lines of quote churn around ~8 lines of real change. Landing a standalone `style:` commit first kept the feature diff reviewable — and made `npm run lint` pass clean for the first time.
- **Verify a "fix" is actually a fix before shipping it.** The dead `margin-top: -var(...)` looked like a bug to repair, but repairing it would have shifted the arrow ~8px against two years of visually-validated rendering. Checking the built bundle showed the declaration was already being dropped, making removal a true no-op and the "repair" a regression.
- **A custom property named `*-color` may not hold a color.** `--ds-auro-popover-boxshadow-color` resolves to a complete box-shadow value (`0px 0px 10px rgba(0, 0, 0, 0.15)`). Consumed whole by `.popover` it works; interpolated into a longhand as if it were a color it produces invalid CSS that is silently discarded. Read what a token actually contains rather than trusting its name — and prefer consuming shadow tokens whole.
- **Auditing one instance of a defect class is worth doing.** The `margin-top` bug was found incidentally. Deliberately scanning the same stylesheets for *other* declarations that never applied turned up the arrow's missing box shadow — a bug that had been invisible for years precisely because its symptom was the absence of something.
- **ADO acceptance criteria are not always in the acceptance-criteria field.** Here `System.Description` and `Microsoft.VSTS.Common.AcceptanceCriteria` were both empty; the real checklist, risks, and testing guidance were in `Microsoft.VSTS.TCM.ReproSteps` and `Microsoft.VSTS.TCM.SystemInfo`.
- **Decide the commit-to-ticket convention before committing, not after.** The formatting commit was made without a ticket reference and had to be reworded afterwards, which meant rewriting history — safe here only because nothing had been pushed. Tagging every commit with the ticket up front costs nothing; retrofitting it costs a rebase.

## Dead Declarations Removed

Two declarations in the component's stylesheets had never had any effect, because in each case the value was invalid. Both were removed in a separate commit; both removals are no-ops at runtime, confirmed against the built bundle and the computed styles of a live popover.

- **`margin-top` on the arrow** (`src/styles/style.scss`) — `margin-top: -var(--ds-size-100, ...)`. The `-` prefix on `var()` doesn't parse, so the declaration was dropped at build time and never reached the browser.
- **`box-shadow` on the arrow** (`src/styles/color.scss`) — `box-shadow: 2px 2px 1px 0 var(--ds-auro-popover-boxshadow-color)`. That variable resolves to `0px 0px 10px rgba(0, 0, 0, 0.15)`, a complete box-shadow value rather than a color, so the declaration expanded to invalid CSS and was discarded at computed-value time. The arrow has therefore never had a shadow. `.popover` consumes the same variable as a whole value and works correctly — the `-color` suffix on a variable holding a full shadow is the trap.

Note what was **not** done: neither declaration was repaired to do what it appeared to intend. Repairing `margin-top` would shift the arrow ~8px, and repairing `box-shadow` would give the arrow a shadow it has never had. Both are visible appearance changes against rendering that has shipped for years with no design reference to validate against, so they belong in a design-reviewed ticket rather than a cleanup commit. Removal keeps the stylesheets honest without changing a pixel — which matters now that consumers are being invited to override these very rules.

## Follow-ups Noticed, Not Fixed

- **The arrow may want a shadow.** The removed `box-shadow` declaration suggests someone intended one. If that is still desired, it needs a design decision about whether the arrow should carry elevation separately from the bubble, plus a correctly-typed token — the existing `--ds-auro-popover-boxshadow-color` cannot be used as a color.
- **No screenshot-based visual regression harness exists in this repo.** Worth a separate infrastructure ticket rather than smuggling it into a component change.
- **`apiExamples/cssParts.html` still sets `box-shadow: none` on the arrow.** Harmless (the default is already `none`), and it does demonstrate that the property is overridable through the part, but it no longer overrides anything real.
- **Nothing asserts the properties `webcorestylesheets` actually contributes.** The `"default appearance"` block covers token- and SCSS-driven properties only; the bubble's padding (`util_insetLg`), type classes, and responsive `max-width` all come from webcore and are untested. That is why the v12 major bump on this branch could not be positively verified — see "The dependency bump, and why it needed checking." Three computed-style assertions would close it.
- **The inset utility is deprecated as of `webcorestylesheets` v12.** `style.scss` still `@use`s `utilityMixins/insetUtility`, which now emits `Deprecated: Inset utility selectors and mixin` on every build. Non-blocking today — the utility still works and the build succeeds — but it will break on a future major. Migrating needs a look at what replaces it in the WebCoreStyleSheets docs, which is out of scope for a styling-contract ticket.

## Iterations That Didn't Work

- **The documentation example shipped broken and had to be rewritten.** The first version used a conventionally-formatted `<style>` block — two-space indentation, blank lines between rules. The docs pipeline turned part of it into a code block inside the `<style>` element, and CSS error recovery silently dropped the `::part(arrow)::before` rule. On the rendered page the bubble restyled and the trigger aligned, but the arrow stayed default white. Fixed by moving every line in the block to column zero and removing the blank lines; verified by enumerating the page's parsed CSS rules and confirming all three now appear.
- **Demonstrating arrow *resizing* in the reference example.** The plan called for it, but the `::before` offsets are hand-tuned to the 12px arrow size, so changing the dimensions visibly pulls the arrow out of alignment with the bubble. Shipping that as the canonical example would have looked like a defect. The example was scoped to recoloring; the resizing caveat moved into prose.
- **A test asserting arrow rotation from the requested placement.** Failed immediately — Popper had flipped the fixture's placement, so `placement="top"` rendered a `bottom`-rotated arrow. Replaced with an assertion derived from `data-popper-placement`.
- **Repairing the dead `margin-top` declaration instead of removing it.** Rewriting `-var(...)` as `calc(-1 * var(...))` would make the declaration finally do what it says — and move the arrow ~8px, changing shipped appearance with no design reference to validate against (a risk the ticket itself flagged). Rejected in favor of deleting the line.
- **Committing the parts work directly.** The first staging attempt would have triggered `lint-staged`'s auto-fix and buried the change in formatting churn. Abandoned in favor of stashing the work, landing a standalone `style: apply biome formatting` commit on a clean tree, then restoring on top — which required resolving one conflict in `render()` where the formatter had rewritten quotes on the same line as the new `part="arrow"` attribute.
- **Reading the ticket without authentication.** `WebFetch` bounced to the Entra sign-in page and the local `az` CLI had no `devops` extension installed. Only the REST API with a PAT worked. Noted because it will recur on every ADO-linked ticket.
